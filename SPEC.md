# StreetPass — техническое задание

## 1. Задача

Android-приложение, которое в фоне обнаруживает других пользователей этого же
приложения по Bluetooth Low Energy и регистрирует встречу. Пользователь в конце
дня открывает приложение и видит, сколько людей встретил.

Аналог StreetPass из Nintendo 3DS, но без обмена профилями.

**Цель MVP:** два физических Android-телефона с установленным приложением
обнаруживают друг друга по BLE, и у обоих в статистике появляется по одной
зарегистрированной встрече.

Вне области MVP: сервер, аккаунты, облачная синхронизация, iOS, обмен профилями.

## 2. Ограничения по приватности (жёсткие)

- GPS и любые Location API не используются. Разрешение на геолокацию на
  Android 12+ не запрашивается вообще (`BLUETOOTH_SCAN` + `neverForLocation`).
  На Android 11 и ниже `ACCESS_FINE_LOCATION` запрашивается вынужденно —
  это требование старой системы для BLE-сканирования, объяснить это в UI.
- Персональные данные не собираются. Идентификатор — случайные байты, не
  связанные с аккаунтом, IMEI, MAC или номером телефона.
- Данные не покидают устройство. Разрешение `INTERNET` используется только для
  проверки обновлений: по нажатию кнопки один GET к GitHub Releases API и, по
  желанию пользователя, скачивание APK. Ничего о встречах, ID или устройстве в
  запросе нет. Других сетевых обращений в приложении быть не должно.
- `android:allowBackup="false"` — база не уезжает в облачный бэкап.
- MAC-адреса и имена устройств не сохраняются и не логируются.

## 3. Стек

Kotlin, Jetpack Compose (Material 3), BLE (advertising + scanning), Room,
DataStore Preferences, coroutines/Flow, foreground-сервис.
minSdk 26 (java.time без десугаринга), targetSdk 35.

DI-фреймворка нет: `AppContainer` в классе `Application` как service locator.

## 4. Протокол обнаружения

### 4.1 Идентификатор

8 байт из `SecureRandom`, хранятся в DataStore в hex. Генерируются при первом
запуске. Пользователь может перегенерировать вручную в настройках.

### 4.2 Рекламный пакет

Legacy advertising, лимит полезной нагрузки 31 байт. Используется 19:

| Поле | Байт | Значение |
|---|---|---|
| Flags | 3 | добавляет стек автоматически |
| Complete 16-bit Service UUID | 4 | `0x5350` |
| Service Data (16-bit) | 12 | 2 заголовок + 2 UUID + 8 байт ID |

`SERVICE_UUID = 00005350-0000-1000-8000-00805f9b34fb` — 16-битный UUID,
развёрнутый по Bluetooth Base UUID. Именно 16-битный: 128-битный занял бы
18 байт и Service Data уже не поместилась бы.

Настройки рекламы: `setConnectable(false)`, `setTimeout(0)`,
`setIncludeDeviceName(false)`, `setIncludeTxPowerLevel(false)`.
Неподключаемая реклама означает, что GATT-сервер не поднимается и подключиться
к устройству нельзя — наружу уходят только 8 случайных байт.

### 4.3 Почему не MAC

Android периодически подменяет MAC-адрес (LE Privacy / RPA). По нему нельзя ни
опознать человека, ни стабильно его посчитать. Личность передаётся
исключительно в Service Data.

### 4.4 Сканирование

Всегда с `ScanFilter` по `SERVICE_UUID`. Это не оптимизация, а требование:
начиная с Android 8.1 система не отдаёт результаты нефильтрованного
сканирования при выключенном экране. Дополнительно фильтр выгружается в
контроллер Bluetooth и экономит батарею.

`CALLBACK_TYPE_ALL_MATCHES`, `MATCH_MODE_AGGRESSIVE`, `reportDelay = 0`.

Из `ScanResult` берутся только `scanRecord.getServiceData(SERVICE_UUID)` и
`rssi`. Всё остальное игнорируется.

## 5. Логика подсчёта встреч

### 5.1 Дебаунс (в сервисе, in-memory)

Реклама прилетает несколько раз в секунду от каждого устройства. Без фильтра
база получала бы сотни запросов в минуту. Повторные пакеты от одного `peerId`
игнорируются в течение 10 секунд. Карта чистится от записей старше 10 минут при
превышении 512 элементов.

### 5.2 Антидубль (в репозитории, персистентный)

Повторная встреча с тем же `peerId` засчитывается не раньше, чем через
`cooldownMinutes` (по умолчанию 60, настраивается 5–240) после предыдущей
**зачтённой** встречи. Поле `lastSeenAt` при этом обновляется на каждом
принятом пакете — в базе видна реальная активность, счётчик не накручивается.

### 5.3 Порог сигнала

Пакеты с RSSI ниже `minRssi` (по умолчанию −95 dBm, настраивается −100…−40)
отбрасываются до обращения к базе. Иначе считались бы люди за стеной или этажом
ниже.

### 5.4 Результат обработки пакета

```
Registered(peerId, firstMeeting) — встреча записана
Cooldown                         — рядом, но уже засчитан в текущем окне
TooWeak                          — сигнал слабее порога
```

## 6. Данные (Room)

```
peers
  peerId          TEXT PK
  firstSeenAt     INTEGER
  lastSeenAt      INTEGER   обновляется на каждом пакете
  lastEncounterAt INTEGER   база для антидубля
  encounterCount  INTEGER
  lastRssi        INTEGER
  bestRssi        INTEGER

encounters
  id            INTEGER PK autoincrement
  peerId        TEXT FK -> peers.peerId ON DELETE CASCADE
  timestamp     INTEGER
  rssi          INTEGER
  firstMeeting  INTEGER (bool)
  INDEX(peerId), INDEX(timestamp)
```

Запись встречи и обновление peer — в одной транзакции (`db.withTransaction`).

Границы суток считаются через `java.time.LocalDate` в локальной таймзоне, не
вычитанием 24 часов. Flow «сегодня» переподписывается в полночь, иначе в долго
открытом приложении дата залипает на вчера.

## 7. Фоновая работа

Foreground-сервис с типом `connectedDevice`. Причина: начиная с Android 8
фоновые процессы усыпляются, а BLE-сканирование из фона без видимого уведомления
система останавливает. Постоянное уведомление — единственный легальный способ
держать сканер живым долго.

Уведомление: канал `IMPORTANCE_LOW`, без вибрации, `setOngoing(true)`,
`setSilent(true)`, текст «Встреч сегодня: N», действие «Выключить», тап ведёт в
приложение.

### 7.1 Duty cycle

Непрерывное сканирование сажает батарею. Профили:

| Профиль | Окно | Пауза | Scan mode |
|---|---|---|---|
| Экономия | 8 с | 112 с | BALANCED |
| Баланс (по умолчанию) | 10 с | 50 с | BALANCED |
| Максимум | непрерывно | — | LOW_LATENCY |

Все профили держатся ниже системного лимита в 5 запусков сканирования за
30 секунд — при его превышении Android молча перестаёт отдавать результаты.
Реклама идёт непрерывно, она почти ничего не стоит.

### 7.2 Реакция на события

- `BluetoothAdapter.ACTION_STATE_CHANGED`: при выключении — остановить радио,
  показать причину в UI; при включении — перезапустить. Ресивер регистрируется
  в рантайме с `RECEIVER_NOT_EXPORTED`.
- Изменение настроек или смена ID — перезапуск радио без остановки сервиса
  (`ACTION_REFRESH`).
- `BOOT_COMPLETED` и `MY_PACKAGE_REPLACED`: если автозапуск включён и обнаружение
  было активно — поднять сервис. Запуск обернуть в try/catch: на Android 15 и
  на ряде прошивок старт foreground-сервиса из BOOT_COMPLETED может быть
  запрещён, это не повод падать.
- `onTaskRemoved`: сервис продолжает работу после смахивания приложения.

## 8. Разрешения

| Версия | Разрешения |
|---|---|
| ≤ 11 | `BLUETOOTH`, `BLUETOOTH_ADMIN` (install-time), `ACCESS_FINE_LOCATION` |
| 12+ | `BLUETOOTH_SCAN` с `neverForLocation`, `BLUETOOTH_ADVERTISE` |
| 13+ | дополнительно `POST_NOTIFICATIONS` |

Плюс `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`,
`RECEIVE_BOOT_COMPLETED`.

Старые `BLUETOOTH`/`BLUETOOTH_ADMIN`/`ACCESS_FINE_LOCATION` объявляются с
`android:maxSdkVersion="30"`.

`POST_NOTIFICATIONS` не блокирует работу: без него сервис работает, просто не
показывает уведомление.

Включение Bluetooth: `ACTION_REQUEST_ENABLE` требует `BLUETOOTH_CONNECT`,
которое приложению не нужно ни для чего другого. Вместо диалога открывать
`Settings.ACTION_BLUETOOTH_SETTINGS`.

Состояние разрешений и Bluetooth перепроверять на `ON_RESUME` — пользователь мог
поменять их в настройках.

## 9. Экраны

Нижняя навигация, четыре вкладки. `navigation-compose` не нужен — достаточно
состояния выбранной вкладки.

### Главная
- Карточка обнаружения: тумблер, статус (передача / сканирование — индикаторы),
  время последнего принятого сигнала.
- Предупреждения: нет разрешений / выключен Bluetooth / ошибка BLE — с кнопкой
  действия.
- Плитки: встреч сегодня, людей сегодня, уникальных всего, встреч всего.
- Последние 5 встреч, переход в историю.
- Свой анонимный ID с пояснением, что он значит.

### История
Список встреч, сгруппированный по датам, заголовок «Сегодня / Вчера / 3 марта
2026 · N». В каждой строке: короткий ID, «Первая встреча» или «Встреча №N»,
время. Лимит выборки 500 — история на экране, а не выгрузка базы в память.
Пустое состояние с объяснением, что делать.

### Статистика
- Сегодня: встреч, людей.
- Последние 7 дней: встреч, людей + столбчатая диаграмма по дням
  (рисовать самому через Box, библиотеку графиков не тянуть).
- За всё время: встреч, уникальных людей, среднее встреч на человека.
- Топ-5 самых частых peer'ов.

### Настройки
- Обнаружение: передавать свой ID / искать других / автозапуск после перезагрузки.
- Профиль энергопотребления: три радиокнопки с описанием.
- Антидубль: слайдер 5–240 мин.
- Порог RSSI: слайдер −100…−40 dBm с пояснением дистанции.
- Приватность: текст о том, что собирается и что нет; тумблер «хранить RSSI»;
  смена ID (с подтверждением); очистка истории (с подтверждением).
- Обновления: текущая версия, кнопка «Проверить обновления». Запрос к
  `api.github.com/repos/<owner>/<repo>/releases/latest`, сравнение `tag_name`
  с `BuildConfig.VERSION_NAME`. Если есть новее — заметки к релизу, кнопки
  «Скачать и установить» (DownloadManager → системный установщик, требует
  `REQUEST_INSTALL_PACKAGES`) и «Открыть на GitHub». Ошибки сети показывать
  текстом, не падать.

### 9.1 Релизы

GitHub Actions по тегу `v*` прогоняет `lint test`, собирает `assembleRelease`
с ключом из секретов репозитория (`versionName` из тега, `versionCode` из номера
запуска) и прикладывает APK к релизу. Обновление ставится поверх только при
совпадении подписи: на телефоны ставить release-сборки, не debug.

## 11. Критерии приёмки MVP

1. `./gradlew assembleDebug lint` проходит без ошибок.
2. Приложение ставится на два физических устройства и запускается.
3. На Android 12+ при выдаче разрешений **не** запрашивается геолокация.
4. При включении тумблера появляется постоянное уведомление, индикаторы
   «передача» и «сканирование» становятся активными.
5. Два устройства рядом обнаруживают друг друга за время не больше одного цикла
   duty cycle, у обоих появляется по одной встрече с корректным временем.
6. Повторное обнаружение в пределах окна антидубля новую встречу не создаёт.
7. При `cooldown = 5 мин` вторая встреча появляется после истечения окна.
8. Статистика «сегодня / неделя / всё время» сходится с содержимым истории.
9. После убийства приложения из списка задач сервис продолжает работать,
   встречи продолжают записываться.
10. Выключение Bluetooth не роняет приложение: показывается причина, после
    включения обнаружение восстанавливается само.
11. Смена ID и очистка истории работают и не ломают текущую сессию обнаружения.
12. В `logcat` нет `SecurityException` и `SCAN_FAILED_*`.

## 12. Порядок работ

1. Скелет проекта: Gradle, манифест, ресурсы, тема, `StreetPassApp` + `AppContainer`.
2. Слой данных: Room (сущности, DAO, база), DataStore (настройки, идентификатор).
3. `EncounterRepository` с логикой антидубля + unit-тесты на неё
   (in-memory Room, фиксированное `now` параметром).
4. `BleAdvertiser` и `BleScanner` изолированно.
5. `DiscoveryService`: foreground, duty cycle, реакция на настройки и
   состояние адаптера. `BootReceiver`.
6. UI: главный экран с тумблером и разрешениями — это минимум для проверки
   на железе. Проверить пункты 1–6 критериев приёмки.
7. История, статистика, настройки.
8. Прогнать полный список критериев приёмки.

## 13. Подводные камни

- **Эмулятор не поддерживает BLE.** Проверка только на физических устройствах.
- **Реклама поддерживается не всеми чипами.** На части устройств
  `bluetoothLeAdvertiser` возвращает `null` — такое устройство сможет только
  находить других. Это не ошибка приложения, но её нужно показать пользователю.
- **Вендорские прошивки** (MIUI, EMUI, ColorOS) убивают foreground-сервисы
  вопреки правилам Android. В README должна быть инструкция снять оптимизацию
  батареи вручную.
- **Лимит на перезапуск сканирования:** больше 5 стартов за 30 секунд — и
  система молча перестаёт отдавать результаты, без ошибки в колбэке.
- **Колбэки BLE приходят не в main-потоке.** Тяжёлую работу и обращения к базе
  уводить в `Dispatchers.IO`.
- **Разрешение может быть отозвано в рантайме**, а адаптер выключен между
  проверкой и вызовом — отсюда обязательные try/catch на `SecurityException`
  и `IllegalStateException` вокруг каждого вызова BLE API.
- **Обе стороны считают встречу независимо.** Подтверждения нет, при
  односторонней потере пакета у одного из пользователей встреча не запишется.
  Это допустимо для MVP, но должно быть в README.

## 14. Возможное развитие (не делать сейчас)

- Ротация ID по расписанию с локальной таблицей соответствия — защита от
  долговременного трекинга по постоянному идентификатору.
- Обмен коротким профилем (ник, эмодзи) через GATT при сближении.
- Экспорт истории в CSV/JSON.
- Экран отладки с сырыми результатами сканирования.
- Автоудаление встреч старше N дней.
- Совместимость с iOS: понадобится GATT-сервер и overflow area.
